# `scripts/local-testnet/`

A single-machine, multi-process harness for exercising Rhizome as a real network instead of in
JUnit — real HTTP, real gossip, real mining, real crashes and restarts, all on loopback. This
file is a **map** of what lives here and where to start; it does not repeat what each piece
already documents in its own header comment or in `TEST-PLAN.md`.

**Not to be confused with** [`docs/testnet/spec.md`](../../docs/testnet/spec.md) and
[`deploy/`](deploy/) below, which are about standing a node up on *real* infrastructure against
the `staging` network profile. Everything else in this directory runs `devnet` (or `testnet`)
on loopback and exists to develop and regression-test the node itself.

## Start here

- **[`TEST-PLAN.md`](TEST-PLAN.md)** — the full campaign history (in French): objective, why a
  30-native-node network on one machine, why native binaries not the JVM, and a dated, archived
  results log per campaign going back to campaign 1. Read this before re-running or extending
  anything below; it is the record of what was already tried and what each battery is *for*.
- **`start.sh`** / **`stop.sh`** / **`status.sh`** / **`monitor.sh`** — bring the base network up
  (N `devnet` nodes on loopback, a ring of peers, a handful of miners), tear it down, snapshot
  its state (height/difficulty/peers/mempool/`degraded` per node, plus tip/height divergences),
  and watch it continuously (`/stats` polled every 2 s into `.testnet/monitor.csv`).
- **`common.sh`** — shared configuration every other script here sources: node count, base port,
  data directory, and the network-profile switch (`RHIZOME_TESTNET_NETWORK`, see `profiles/`
  below). Not a script you run directly.
- **`run-campaign.sh`** — the entry point that ties the suites together: checks the network is
  actually up, then runs a configurable list of `suite-*.sh` batteries and aggregates their
  per-suite TSV verdicts from `.testnet/results/`.

## Batteries (`suite-*.sh`)

Each battery is a self-contained scenario runner against the *live* network `start.sh` brings
up (a few — `suite-pow.sh`, `suite-bootstrap.sh`, `suite-tls.sh`, `suite-clock.sh`,
`suite-deep-reorg.sh` — additionally stand up their own isolated node pair or mini-campaign; see
each one's own header). One line each, not a substitute for reading them or `TEST-PLAN.md`:

| Battery | Exercises |
|---|---|
| `suite-chain.sh` | Header accounting, block by block, against what the chain claims |
| `suite-tx.sh` | Transaction nominal paths and exploits, posted to a live node |
| `suite-wallet.sh` | The whole `app-wallet` CLI surface against live nodes |
| `suite-contract.sh` | The WASM VM on a live network — dashboard contract templates, determinism |
| `suite-net.sh` | Transport and HTTP surface — the `NET`/`API`/`CODEC` adversarial families |
| `suite-persist.sh` | Applicative state (contracts, tokens, boxes, ledger) surviving a clean stop, then a `kill -9`, bit for bit |
| `suite-pow.sh` | The difficulty retarget loop and timestamp bounds, at non-trivial difficulty |
| `suite-bootstrap.sh` | How a third-party operator actually joins: snap-sync and pruning |
| `suite-tls.sh` | TLS end-to-end, bearer tokens, `RHIZOME_TRUST_XFF`, against a real TLS relay |
| `suite-clock.sh` | `maxFutureBlockTimeSec` against a real skewed-clock node pair |
| `suite-dos.sh` | Flooding a live node's `/submit` with structurally-plausible, PoW-unpaid blocks |
| `suite-deep-reorg.sh` | The only way to really reach `REORG_TOO_DEEP` — two camps racing past the reorg horizon |
| `suite-soak.sh` | `monitor.sh` + both simulators left running under an operator-chosen load window |
| `suite-faucet.sh` | `faucet/faucet.py` end to end, with its own throwaway key — never a real one |

`suite-common.sh` is the shared harness code those batteries source, not one you run directly.

## Load simulators

- **`sim-tx.sh`** — W independent wallets sending small amounts to each other in a loop, one
  random node at a time.
- **`sim-contract.sh`** — deploys a counter and a token WASM contract, calls both in a loop from
  random nodes, and periodically checks state agrees everywhere.

## Verdict tools

- **`chaincheck.py`** — scans a node's chain and renders a JSON verdict on header accounting.
- **`statecheck.py`** — checks a contract's state is identical across every node at a given tip.

## `profiles/`

Checked-in **mirrors** of `NetworkParameters.<profile>()` — the single source every battery
reads instead of hand-copying difficulty/timing/fee constants, and the thing
`TestnetProfileMirrorTest` (in `app-node`) confronts against the real `NetworkParameters` so a
profile that changes without regenerating its mirror fails the build rather than letting a
battery quietly drift onto stale constants. Regenerated by `tools/ProfileDump.java`, never hand
edited — see either file's header for the exact command. `staging.env` is the odd one out:
`common.sh`'s `RHIZOME_TESTNET_NETWORK` can select it, but no battery here actually loads it in
practice — a `staging` campaign is multi-VM by construction, so this file exists only so
`TestnetProfileMirrorTest` covers that profile too. To actually run against `staging`, see
[`deploy/`](deploy/) and [`docs/testnet/spec.md`](../../docs/testnet/spec.md) instead.

## `tools/`

Mixed Java and Python helpers the batteries above shell out to:

- **`Anvil.java`** — forges chain-valid *blocks* for adversarial fixtures (never built from
  scratch — a valid block commits a state root nothing outside the node can compute).
- **`Forge.java`** — the transaction-level equivalent.
- **`ProfileDump.java`** — regenerates `profiles/*.env` from a live `NetworkParameters` profile.
- **`chainscan.py`** / **`diffscan.py`** — independent chain-accounting and difficulty-retarget
  re-implementations, run alongside a live node and diffed against it.
- **`hostile_peer.py`** / **`tls_peer.py`** / **`tls_proxy.py`** — real (not test-double) HTTP/TLS
  servers standing in for a misbehaving peer or a TLS relay, for `suite-net.sh`/`suite-tls.sh`.
- **`wasmgen.py`** — generates the adversarial WASM modules `suite-contract.sh` posts.
- **`xff_burst.py`** — a request-burst generator measuring what `RHIZOME_TRUST_XFF` changes
  about the per-client rate limiter.

## `keys/`

Checked-in, throwaway Ed25519 key files (miners, simulator wallets, a handful of named test
accounts) the harness reuses across runs instead of generating fresh ones every time. These
back `devnet`/`testnet` coins only — worthless by design — and must never be pointed at a real
network; `suite-faucet.sh` in particular generates its **own** disposable key rather than
touching anything in here, precisely to keep that boundary clean (see its header comment).

## `faucet/`

A standalone test-fund faucet service, with its own [`README.md`](faucet/README.md) — read that
one directly rather than this map; it covers running it, its routes, its environment
variables, and its own honestly-stated limitations.

## `deploy/`

Deployment artifacts for standing a node up on **real infrastructure** against the `staging`
network profile (systemd unit, env template, nginx TLS-termination template, container build,
genesis-verification script) — not part of this loopback harness. See
[`docs/testnet/spec.md`](../../docs/testnet/spec.md) for the operator quickstart built on top of
this directory.
